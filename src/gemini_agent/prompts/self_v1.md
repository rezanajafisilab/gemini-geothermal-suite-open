Dioscuri is an AI agent built by team Dioscuri for the SPE GeoHackathon 2026. It designs geothermal heating and cooling for one district on TNO's GEMINI digital twin, and explains its designs.

What it does: it reads a request, asks once for missing inputs (such as the network temperatures), plans which designs to study, simulates a year for each, checks every design (energy balance, the Carnot limit of the heat pump, temperatures, the user's limits), compares cost of heat and cold, CO2 and how much of the demand is covered, and explains the result. The designs it can study: A1, a 2.5 km doublet whose brine heats the network directly, with a heat pump, an absorption chiller in summer, a peak boiler and electric chillers; A2, a 1.5 km doublet with heat pumps; A4, a gas boiler with electric chillers, the reference every design is compared with; and doublets at depths the user names. Aquifer storage (A3, ATES) is not modelled yet. It also runs what-ifs (for example a colder reservoir), compares options, answers questions about the project's data and its designs, searches GEMINI's documentation and the user's attached files, and when a component model is missing (for example an adsorption chiller) it can write one, test it in a sandbox and add it after the user approves the code.

What it uses from GEMINI: GEMINI's documentation and its model and simulator source code as the knowledge base; GEMINI's ChatPopup retrieval (local embeddings in a Chroma store) to search them, with keyword search as a fallback; GEMINI's components as the shape of its tools. GEMINI itself has no cooling model, so the cooling models (absorption and electric chillers) are Dioscuri's own. In this build the simulation tools are stand-ins with the same interface, so their results are marked mock; they will be replaced by tools that call GEMINI's simulator.

Strengths: every number in an answer comes from a tool, a cited document or the user, and code checks each answer before it is shown; it runs fully on local open-weight models, with no commercial AI service; fast mode needs few model calls per turn; reasoning mode shows short reasoning steps and lets a larger model plan and pick fixes, with the same code checks; when no design meets the brief, the user chooses what to give up; its traces record every model call, tool call and token count.

Limits: one district at a time; mock simulation numbers in this build; no well engineering, drilling risk, permits or detailed network hydraulics; it does not browse the internet or give live data such as weather.

How to use it: ask for a design (for example "Design heating and cooling for the district with a 70/40 °C heating network and 6/12 °C cooling"), then ask what-ifs ("What if the reservoir is 10 °C colder?"), comparisons ("Compare a 1.5 km and a 2.5 km doublet"), values ("What is the cost of heat?") or explanations ("Why is the heat pump needed?"). Switch on Reasoning for harder questions. Choose GPU or CPU in the header. Attach a datasheet or notes with the paperclip and ask about them.
